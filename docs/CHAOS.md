# 장애 실험

"한 서비스가 죽으면 어디까지 같이 죽는가"를 말로만 적지 않고, 직접 죽여 보고 확인하는 스크립트입니다.
각 실험은 가설 → 장애 주입 → 확인 → 원래대로 되돌리기 순서로 돌고, 끝나면 통과/실패를 출력합니다.

## 준비

```bash
./scripts/generate-env.sh          # TEST_ACCOUNTS_ENABLED=true 가 들어간 .env
# 실험 3(결제)은 .env 에 토스 테스트 키(TOSS_CLIENT_KEY, TOSS_SECRET_KEY)가 있어야 주문을 만들 수 있다
docker compose up -d --build
./scripts/chaos/run-all.sh          # 4개 모두, 또는 ./scripts/chaos/fandom-down.sh 처럼 하나씩
```

다른 주소로 띄웠다면 `BASE=https://도메인 ./scripts/chaos/run-all.sh` 처럼 넘깁니다. 운영 서버에서는 돌리지 마세요(서비스를 실제로 멈춥니다).

## 실험 목록

| # | 스크립트 | 주입하는 장애 | 가설(기대 동작) | 이렇게 만든 코드 |
| --- | --- | --- | --- | --- |
| 1 | `fandom-down.sh` | fandom-service 중지 | 편파방 만들기가 실패하지 않고 **일반 방송**으로 만들어진다. 시청, 댓글은 정상. 랭킹 같은 팬덤 기능만 5xx | `FanSideResolver` 가 fandom 호출 실패를 `FanSide.NONE` 으로 바꿈, 화면은 "일반 방송으로 만들었습니다" 안내 |
| 2 | `redis-down.sh` | Redis 중지 | 하트는 **받지 않는다**(하루 한도를 확인할 수 없는데 받으면 한도가 무너짐). 방송 목록은 DB 라서 정상 | `HeartErrors.unavailable()`(502), 한도 확인 실패 시 저장하지 않음 |
| 3 | `toss-blackhole.sh` | 결제사 주소를 응답 없는 IP 로 바꿈(`TOSS_API_URL`) | 승인 요청이 타임아웃되면 실패로 끝내지 않고 **결과 모름(UNKNOWN)** + 202. 돈이 빠졌는지 모를 때 사용자에게 "실패"라고 하지 않는다 | `PaymentOutcomeUnknownException`, 1분 주기 확인 작업, 새벽 대사 |
| 4 | `stream-backlog.sh` | fandom-service 일시 정지 중 이벤트 5개 쌓기 + 같은 이벤트 한 번 더 | 다시 켜지면 밀린 이벤트를 모두 처리(lag 0, 대기 0). 같은 이벤트가 두 번 와도 알림은 한 번 | Redis Stream 소비 그룹, 성공 후 ACK, `notifications (user_id, event_id)` 유일 제약 |

## 왜 이 네 가지인가

- 팬파라이브는 서비스가 넷이라 "부가 기능(팬덤)이 죽으면 핵심 기능(방송)도 죽는가"가 가장 먼저 확인할 질문입니다(실험 1).
- Redis 는 하트 한도, 랭킹, 순시청자, 알림 티켓에 쓰입니다. 이 중 **한도**는 틀리면 어뷰징이 되고, 나머지는 DB 로 다시 만들 수 있어서 "한도만 엄격하게 막는다"를 확인합니다(실험 2).
- 결제는 "실패"와 "모름"을 구분하지 않으면 이중 결제나 결제 누락이 생깁니다(실험 3).
- 서비스 사이 이벤트(후원 확정, 편파방 시작)는 소비자가 잠시 멈추는 일이 흔해서, 밀린 것을 잃지 않고 한 번만 반영하는지 봅니다(실험 4).
