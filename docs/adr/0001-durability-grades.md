# ADR 0001. 데이터마다 내구성 등급을 다르게 둔다

- 상태: 채택 (2026-11-17)
- 관련: `HeartAccumulator`, `DonationService`, `DonationStreamRelay`, `RedisViewerCounter`

## 배경

팬파라이브에는 성격이 전혀 다른 데이터가 같이 흐릅니다.

- 후원: 돈이 오간다. 하나라도 빠지거나 두 번 들어가면 안 된다.
- 하트: 무료 재화. 경기 중 특정 순간(두산 베어스 홈런 같은)에 한 팀으로 몰린다.
- 시청자 수: 화면에 보여 주는 참고 값.

모두 "커밋된 뒤 응답"하는 같은 방식으로 저장하면, 하트처럼 몰리는 데이터가 DB 행 잠금 경합을 만들고 그 영향이 후원 같은 중요한 쓰기까지 번집니다.

## 결정

| 등급 | 데이터 | 원본 | 허용하는 손실 | 방법 |
| --- | --- | --- | --- | --- |
| A | 후원(결제) | interaction_db `donations` | 0 | 주문 행 잠금, order_id/payment_key 유니크, 결제사 멱등키, 결과 모름(UNKNOWN) 상태와 조회 확정, 매일 결제사 대사 |
| A' | 랭킹에 반영된 후원 점수 | A 에서 파생 | 일시적 누락 허용, 하루 안에 보정 | 커밋 뒤 Redis Stream 발행, 소비자 PK 멱등, 매일 04:10 결제 원본 합계와 대사 |
| B | 하트 | fandom_db `heart_logs`, `target_stats_daily` | 서버가 갑자기 죽을 때 최대 200ms 분량 | 한도는 Redis Lua 로 요청 안에서 확정, 반영은 200ms 모아서 배치. 정상 종료 시 큐를 비움 |
| B' | 실시간 순위(Redis ZSET) | B 와 A' 에서 파생 | 어긋나도 됨 | 매일 0시 DB 기준 재계산 후 RENAME 교체 |
| C | 순시청자 수 | Redis HyperLogLog | 근사치(약 0.81% 오차), Redis 유실 시 초기화 | 보조 정보로만 표시 |

## 버린 대안

- **하트도 요청마다 DB 반영**: 가장 단순하지만 한 행에 쓰기가 몰리면 잠금 대기가 길어지고 커넥션 풀이 고갈된다.
- **하트를 Redis 에만 두고 DB 는 나중에**: Redis 가 날아가면 복구할 원본이 없다.
- **후원 이벤트를 별도 발행 테이블에 저장하고 재시도**: 이 규모(서버 1대)에서는 하루 한 번 결제 원본과 맞추는 것으로 같은 결과를 더 적은 부품으로 얻는다.

## 결과

- 하트 몰림이 결제 경로에 영향을 주지 않는다.
- 운영 화면의 "반영 1번당 하트 수"로 병합 효과를 바로 볼 수 있다.
- 하트 200ms 유실 가능성은 화면에 드러나지 않는 수준이며, 문서로 명시해 두었다.
